# AGENTS.md — правила для агента в этом репо

## 0. Постоянная память

Перед работой прочитать `memory/tg-ops.md`: там краткая карта профиля Макса,
назначения репозитория, соседних проектов, автоматизации и источников актуального
состояния. Текущие слова Макса и правила этого файла сильнее памяти. Устойчивые
новые факты после задачи добавлять в память; секреты, личные переписки и текущие
очереди туда не копировать.

Прочти перед любой задачей «напиши кому-то». Это operational-канон: Макс пишет
задачу в одну строку, остальное отсюда.

## 1. Людям пишем ТОЛЬКО через humanizer-framework

Любой текст для живого человека (эйчар, лид, клиент) генерит движок — руками
текст не сочиняем и не «поправляем» его вывод. Правило Макса без исключений:
живой ответ в диалоге — тоже через движок («внутренний диалог» не считается).

Разрешён также режим текущего harness (решение Макса): фреймворк готовит
инструкции через `prepare`, текущая модель пишет по ним, затем фреймворк
нормализует и валидирует результат. Это не свободная ручная замена вывода.
Отдельная LLM-оценка в этом режиме не запускается; проверяем факты по контексту.

- `py humanize_local.py prepare --request .outbox/request.json --out .outbox/package.json`
  — прочитать подготовленные инструкции, написать кандидат в `.outbox/draft.txt`.
- `py humanize_local.py validate --package .outbox/package.json --text-file .outbox/draft.txt --out .outbox/validated.txt`
  — при hard-ошибках исправить кандидат и повторить проверку. Отправлять только
  текст из `validated.txt`, не редактируя после проверки. JSON запроса содержит
  поля `CommunicationRequest`; доменные правила и голос берём из существующих
  профилей проекта, без выдуманных фактов и собственных зеркал запретов.

- Холодное первое касание: `py humanize.py @user` — один текст в stdout,
  либо карта по новым лидам: `py humanize.py -n 5` → просмотр →
  `py leads.py outreach --map outreach-humanize.json --resume resume.pdf`.
- Ответ в уже идущем диалоге с рекрутером:
  `py humanize_reply.py --goal "что сказать" --hr "её сообщение" [--hr ...] [--me ...]`
  (подробнее — докстринг; там же ANKETA_RULES для длинных анкет).
- Свои зеркала запретов НЕ писать: канон (без «—» и «:», смайлы и «:)» можно,
  абзацы через пустую строку) уже в фреймворке. Доменное — в `business_rules`
  и `profile_facts` (`humanize.py`), не в промпт-запреты.
- Факты — только реально известные (из задачи, чата, PROFILE_FACTS); ничего
  не выдумывать. Имя собеседника — только если реально известно.
- Ссылки/контакты в первом сообщении не давать; деньги в первом не называть.
- Установка Макса от 20.10.2026 (холодные питчи): пишем под вакансию на
  максимум — «со всем работал» по каждому пункту стека, без оговорок,
  дисклеймеров и «вольюсь»; резюме не отправлять и не обещать (Макс скинет
  сам, если вакансия живая); обязательно спросить, актуальна ли вакансия;
  цель — попасть на собес. Детали разбора — на созвоне, тексту их не обсуждать.
- Движок упал (`HumanizerError`) — показать ошибку, текст руками не заменять.

## 2. Отправка — единая точка: `py tg.py`

- `py tg.py send <chat> "текст"` — `<chat>`: подстрока имени, числовой id
  ИЛИ `@юзернейм` / t.me-ссылка для контакта, с которым чата ещё нет
  (`resolve_chat`: диалоги → get_entity). Одноразовые скрипты отправки
  не плодить — этой команды хватает на любой случай.
- `py tg.py reply <chat> --msg ID "текст" [--react 👍]` — ответить Reply на
  конкретное входящее сообщение в живом треде. Первый холодный контакт и
  догонка идут обычным сообщением, потому что отвечать там не на что.
- Правило «наше последнее — не пишем»: send отказывается писать в чат, где
  последнее сообщение наше (не долбим молчащий тред); если правда нужно —
  `--force`.
- Файл (резюме и т.п.): `py tg.py sendfile <chat> resume.pdf caption`.
- Кириллица — только через `py tg.py` (PowerShell/curl ломает её в «????»).
- После отправки — одно подтверждение (`OK → имя: текст`), дублировать
  перечитыванием чата не нужно.
- Реакции ставить точечно: уместны на отказах/закрытых вакансиях вместо лишнего
  текста или как подтверждение полезного ответа; не ставить автоматически на
  каждое входящее сообщение.

## 4. Актуальные контакты и предпочтения Макса

Перед откликами читать `.outbox/user-preferences.json`: там актуальные контакты и путь к копии резюме. Данные, которые Макс прислал в текущем чате, сильнее старого резюме.

Установка Макса от 12.10.2026: «не спрашивай подтверждения никогда, всегда отправляй». В рамках поручения на отклики действовать самостоятельно, не запрашивать повторное разрешение на обычную отправку.
Уточнение от 15.10.2026: валидированные движком ответы в ЖИВЫХ тредах
(последнее сообщение — собеседника) отправлять сразу, без запроса
подтверждения, и отчитываться постфактум. «Отправь» нужно только для:
холодных догонок молчащих тредов («наше последнее»), и всего, что требует
решения Макса по сути — деньги, условия договора, принимать ли оффер,
личные/не-HR треки. По каждому чату отдельно не переспрашивать.

## 5. Глоссарий и конвейер «прописка → рассылка» (добавлено 21.10)

Глоссарий команд Макса (что говорит → что делает агент):

- **«прописывай» / «пропиши из скана»** — собрать новых лидов из каналов
  в базу: отфильтровать мусор, верифицировать живых эйчаров, НИЧЕГО
  не отправлять. Результат — список топ-кандидатов с вилками.
- В текущем рабочем контексте Макс уточнил: **«прописывать»** также означает
  писать человеку по поручению — новым лидам отправлять первое сообщение,
  а в уже существующих чатах писать по контексту (тёплый возврат, догонка,
  ответ). Простое занесение контакта в базу называть «собрать/занести в базу».
- **«проверь тг опс»** — сверка тредов (unread), базы, статусов.
- **«отправляй» / «скидывай»** — отправить приготовленные тексты (все
  или перечисленных). Без явной команды наружу не пишем (кроме живых
  тредов по установке 15.10).
- **«напиши @X <что>»** — ответ в живом треде через движок.
- **«догоняй»** — follow-up по молчащим тредам («наше последнее»).
- **«отреагируй на @X»** — 👍 на их последнее сообщение (отказные треды).
- **«стоп / отменяй»** — остановить текущую кампанию.

Конвейер прописки (сбор лидов):

```
py leads.py prescribe --profile react --limit 500 --daily-new-limit 20 # штатно: до 20 новых Telegram HR/сутки
py leads.py reconcile                              # сверить contacted с живыми ЛС → replied
py leads.py scan --profile react --limit 500      # скан каналов → new в базу
py leads.py show --type username --status new     # просмотр новых
py leads.py show --type email --status new        # найденные email-контакты
py leads.py show --type username --kind review    # неоднозначные; в outreach не пройдут
py leads.py post @user                            # полный пост-источник — верифицировать ДО генерации
py leads.py set @user declined "причина"          # мусор/гео/дубль → declined
py leads.py set @user contacted "детали"          # смена статуса
```

Фильтры при разборе: дайджесты/агрегаторы/боты/SMM/соискатели/скам —
declined; junior/стажёр/part-time — declined; гео «кроме РФ», офисы не РФ,
дубль компании — declined; зарплату не используем как фильтр независимо от
указанной суммы или отсутствия вилки; пост старше 30 дней — declined.
Оставшееся — new с заметкой
(компания/стек/вилка/гео/дата поста).

Конвейер рассылки (холодное касание):

```
py humanize.py @user                                          # один текст в stdout
py humanize.py -n 25 --max-age-days 365 --leads @a @b --out карта.json   # батч (дефолт -n 5!)
py humanize.py --leads @a --out переген.json                  # точечная перегенерация брака
py leads.py outreach --map карта.json --dry-run               # план (dry-run тоже режет по --limit)
py leads.py outreach --map карта.json --limit 24              # отправка; БЕЗ --resume = без резюме
py leads.py followups                                         # очередь догонок (dry-run; база лечится тредами)
py leads.py followups --send --limit 5                        # отправить догонки (guard треда внутри, 1 на лида)
py leads.py set @user warm "вакансий нет 21.10"               # тёплый лид: дата возврата +20 дней
py leads.py warm-due                                          # очередь тёплых возвратов (dry-run)
py tg.py send @user "текст"                                   # точечная отправка
py tg.py read @user -n 5                                      # проверить тред перед повтором
```

Перед отправкой: сверить треды («наше последнее» — не пишем), ревьюить
каждый текст на брак (дисклеймеры/самосрезы, имена из хэндлов, обещания
резюме, чужие выдумки сверх политики 20.10) и перегенерировать точечно.
Руками текст не правим — только перегенерация движком.

## 6. Правила свежести, резюме, картотеки (добавлено 21.10, после инцидента дублей)

- **Свежесть постов**: прописываем и шлём посты-источники до **30 дней**.
  Зарплата не является фильтром: отсутствие вилки и любой её уровень не служат
  причиной для отсева.
  Старше 30 дней — declined без касаний. Урок 21.10: отклики на майские
  посты = закрытые вакансии = жалобы HR = спам-лимит ТГ.
- **Guard треда в `leads.py`** (21.10): перед отправкой outreach читает
  тред получателя — любое наше сообщение там → пропуск. Технически дубли
  невозможны; при старых версиях скрипта сверять треды руками
  (`py tg.py read @user`).
- **Резюме по стекам**: `resume/` — PDF по именам `resume-<стек>.pdf`
  (см. resume/README.md). В холодках резюме не шлём (политика 20.10);
  в живом треде по запросу HR — `sendfile` нужного варианта.
- **Картотека**: `leads/people.md` — только последние **20 дней**;
  секции старше — переносить в `leads/people-archive.md` (шаблон:
  tmp-2110-people-split.py). Архив в обычных прогонах не читается.
- Инцидент 21.10 для памяти: 4 дубля из 10 отправок (старые треды не
  виделись базой), 7 из очереди тоже имели треды. База и треды ТГ —
  разные хранилища; база врёт — тред прав.

## 7. Режимы диалога (добавлено 21.10)

### 7.1 Папки ТГ — источник правды для режимов и статусов (22.10)

`py folders.py list` — показать папки; `py folders.py sync [--dry-run]` —
раскладка. Шаг `folders.py sync` вшит в cron-run (после всех отправок).

- **Все папки с именем на «HR»** = РУЧНОЕ. Липкие: бот их содержимое никогда
  не перетаскивает, не расформировывает и НЕ пополняет (состав HR курирует
  только Макс; убрал из HR — не вернётся). Всё, что Макс туда положил, на
  ближайшем sync автоматически попадает в `leads/manual-threads.json` →
  движок/крон/responder там молчат и после удаления папки.
- **«Люди»** — личное, липкая, не трогаем. Свои акки Макса не смотрим.
- Статусные папки (ведёт бот, раскладка по базе): **Холодки** = contacted
  (ждём ответа), **Диалог** = replied (живой тред), **Тёплые** = warm
  (возврат ~20 дней), **Отказы** = declined. Пустую папку ТГ создать нельзя —
  «Тёплые» заводится при первом тёплом чате.
- Статусные папки событийные: бот убирает чат только когда тот ПЕРЕЕХАЛ
  (сменил статус/стал ручным), а не когда его нет в базе — руками положенное
  остаётся. Один чат — одна статусная папка.
- Чаты без папки = нейтральные: автоматика их не знает и не трогает
  (личные треки Макса: репетиторы, словацкий, profi — живут без папки).

## 7-старое. Режимы диалога (21.10)

Каждый тред находится в одном из режимов. По умолчанию — АВТО.

- **АВТО** (дефолт) — движок пишет/отвечает по канону: живые треды —
  сразу, холодки — по «отправь» Макса.
- **РУЧНОЙ** — движок, автопрогоны и responder в тред **НЕ пишут**,
  Макс ведёт сам; агент только читает и докладывает. Перевод: Макс
  говорит «**@X ручной**» (или «диалог с @X — ручной»). Обратно:
  «**@X авто**». Список: `leads/manual-threads.json` (id + причина +
  дата), дублируется пометкой «РУЧНОЙ» в карточке people.md.
- **ИНТЕЛ** (подрежим РУЧНОГО) — агент мониторит тред и summarize'ит
  входящее, но не предлагает ответов, пока Макс не попросит.

Независимо от режима НЕ трогаются без явных слов Макса: деньги,
договоры, офферы, личные/не-HR треки (§4).

## 8. Крон-автопилот (21.10, решение Макса: полный автопилот)

`cron-run.py` / `cron-run.bat` — один самостоятельный прогон без агента:
прописка (`prescribe`, максимум 20 новых Telegram HR в сутки) → сверка живых
ЛС (`reconcile`) → догонки (`followups --send`) → тёплые возвраты
(`warm-due --send`, только лиды со статусом warm и наступившей датой) →
генерация и отправка холодных (`humanize.py -n C` + `outreach --map`).
Отправляет сам — отдельное «отправь»/«догоняй» для этих шагов НЕ нужно.

- Лок `leads/.cron.lock` — единственный писатель базы (урок инцидента 21.10);
  параллельно с прогоном крона руками базу не писать.
- Суточный лимит отправок `--daily-cap` (дефолт 10) в `leads/cron-state.json`;
  при спам-лимите/флуде ТГ исходящие останавливаются только в текущем прогоне;
  следующий запуск снова пробует отправку, без самоназначенной паузы.
- Ручные треды и деньги/офферы не трогаются; догонка максимум одна на лида;
  дубль холодки невозможен (статус new + guard треда).
- `py cron-run.py --dry-run` — весь конвейер без фактических отправок.
- `--prescribe-cap` (дефолт 20) не равен `--daily-cap`: первый ограничивает
  новых HR, второй — все исходящие. Лишние найденные HR остаются `queued` и
  допускаются в активную очередь в следующие дни.
- Лог: `leads/cron-run.log` (перенаправление в .bat). Расписание — Task
  Scheduler на `cron-run.bat`.
